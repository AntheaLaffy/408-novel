# 第01章 空指针

2026年3月10日，星期二，上午九点四十。

陆沉正在改一个导出接口的 bug。

客户叫启明零售，做连锁便利店的，全国一千多家门店。他们每个月十号早上要拿到上个月的对账单，财务拿去和供应商核账，晚一天，区域经理的电话就会打到商务那边，商务再打到项目经理这边，项目经理再在群里 @ 陆沉。

这次的问题出在“创建人”这一列。

凌晨两点十七分，定时任务跑完，日志里一片红。陆沉早上到工位第一件事就是翻日志，翻到第三屏，看见一行熟悉得让人想笑的东西：

```
java.lang.NullPointerException: Cannot invoke "com.yunshu.user.User.getName()"
because the return value of "com.yunshu.user.UserClient.getById(Long)" is null
    at com.yunshu.report.mapper.ReportRowMapper.toRow(ReportRowMapper.java:118)
```

空指针。

他大学第一次听老师说“空指针是 Java 程序员最好的朋友”的时候，还觉得这句话挺幽默。现在他不这么觉得了。现在他觉得空指针是那种每年过年都要来你家坐一会儿的亲戚，你不能赶他走，还得给他倒水。

他没有立刻去看代码。

他先点开了右边那一栏。

灵犀的侧边栏是浅灰色的，像一张写了很多遍又擦干净的纸。光标停在报错的那一行，下面自动浮出一段提示：

> **检测到可能为空的对象访问**
> `user.getName()` 存在空引用风险。
> 建议改为：
> ```java
> String creatorName = user == null ? "-" : user.getName();
> ```
> 是否应用？预计耗时 8 秒。

下面两个按钮，**应用** 和 **忽略**，蓝得很有礼貌。

陆沉盯着那行代码看了两秒。

他知道这不对。他也说不清哪里不对。他只是有一种很模糊的、像牙缝里塞了东西的感觉：这个报错说的是“用户是空的”，但一张对账单上为什么会有一个空的用户？

不过这种感觉很快被另一种东西盖过去了：项目经理在群里问，十点前能不能好。

他点了“应用”。

八秒之后，IDE 里多了一行判空，红字没了，编译通过。他重新跑了一遍本地任务，导出成功，Excel 打开，两千多行数据整整齐齐。他把文件发到测试群，说“修好了，麻烦验证”。

九点五十八分。他甚至还来得及去接了杯水。

十点二十，测试回来了。

不是“通过”，是一张截图。截图上，创建人那一列，有一百多行显示着一个横杠。

“陆工，这些是什么？”

陆沉把截图放大，一行一行往下看。

那一百多行集中在同一个时间段，客户名称是“启明零售-华东二区”。他查了查，都是同一个人录的单据。他把工号复制出来，去用户中心查，接口返回：

```json
{"code": 200, "message": "success", "data": null}
```

200。成功。数据是空的。

他又查了第二个、第三个、第十个，全一样。

那一瞬间，他明白问题在哪儿了。

这一百三十七个人，都是已经离职的员工。他们离职之后，账号在用户中心被注销，注销的逻辑是“删掉这条记录”，而不是“标记为已删除”。于是任何按 ID 去查他们的人，都会拿到一个 200 和一个 null。系统认为这是一次成功的查询，只是恰巧什么也没查到。

而启明零售的对账单，需要保留历史单据上的创建人姓名。财务不接受横杠，也不接受“未知用户”。他们要的是那个已经离职的、叫“周敏”的人的名字。

陆沉坐在椅子上，慢慢地靠回椅背。

灵犀给他的答案，没有错。

灵犀只是回答了一个错误的问题。

他问的是“怎么让这个异常消失”，灵犀就给了他一行判空。异常消失了，报表能导出了，工单可以关了。至于那一百三十七行横杠，那不是异常，那是“业务表现”，系统不会报警，只有人会。

但灵犀也没有能力发现真正的问题。

它的任务范围只有 report-export 这个仓库。用户中心的库不在它的上下文里，上游的字段变更它看不到，接口文档也没有同步。单元测试里的 mock 永远返回一个用户，回归测试也没有覆盖“用户被物理删除”的情况。评审 Agent 只检查 diff 和现有测试，测试是绿的，它就通过了。

失败的不是一个模型，是一条流程：工具权限、测试覆盖、跨系统依赖、结果验收，每一环都差一点。而陆沉自己，早上也点了“应用”。

他重新打开代码，开始往上翻调用链。

`ReportRowMapper` 调 `ReportService`，`ReportService` 调 `UserClient`，`UserClient` 是基础平台部维护的 SDK，SDK 里面封了一层 Feign，Feign 后面是用户中心的 `/internal/users/{id}`。再往上，是两年前某次“统一用户体系”的重构，那次重构之后，全公司有十几个地方在查用户，每一个地方都默认“查得到”。

他把这十几个调用点一个个点开。

有的地方判了空，有的地方没判，有的地方判了空然后用 `Optional.ofNullable().orElseThrow()` 抛了个自定义异常——那等于没判，只是把 NPE 换成了一个看起来更有文化的错误。

他忽然想起周晓枫说过的一句话：我们不是在一个系统里工作，我们是在十个系统的接缝里工作。

十一点，他开始找替代方案。

用户中心不能改，那边排期排到四月。基础平台部的同事在群里回复得很客气：“这个属于历史数据兼容问题，我们评估一下。”——在公司语境里，“评估一下”约等于“今年别想了”。

他去翻数据仓库，找到一张 HR 的员工快照表，每天凌晨同步一次，里面有工号、姓名、在职状态。表很脏，字段名叫 `emp_nm`、`stat_cd`，注释是空的，但数据是全的。

他写了一段取数逻辑：先按用户 ID 查，查不到就拿单据上的工号去快照表兜底，兜底再查不到，才显示“已注销用户”。

写完是下午两点。他没吃午饭。

三点，测试环境跑通。四点，客户在群里回了一个“OK”。

四点二十，他提交了代码。

提交信息他想了半分钟，最后写的是：

```
fix: 导出对账单创建人为空时使用员工快照兜底
```

蒋文斌是在四点半找他的。

组长站在他工位旁边，手里拿着手机，屏幕上是他刚提交的那个 MR。

“修好了？”

“修好了。”

“花了多久？”

陆沉算了一下：“从早上到刚才，大概四个小时。”

蒋文斌点点头。

“四小时，一个空指针。”

“不是空指针，”陆沉说，“是上游注销用户的时候把记录删了，我们这边十几个地方都默认查得到——”

“我知道。”蒋文斌打断他，“我看你 MR 描述了。”

他顿了一下。

“我的意思是，下次别让它变成四个小时。”

陆沉张了张嘴。

他想说，这四个小时里，有一个小时是在找那一百三十七行数据从哪儿来的，一个小时是在翻调用链，剩下两个小时在补上游的坑。他想说，如果他早上没有点“应用”，如果他没有先问一句“这个 user 为什么会是 null”，这四个小时本来可以变成二十分钟。

但这些话在嘴里转了一圈，最后变成了一句：

“好。”

蒋文斌拍了拍他的肩，走了。

---

下午五点五十，部门大群里弹出一条消息。

发消息的是部门的行政，标题很长：

**《2026 年 2 月 AI 代码采纳率排行榜（部门）已更新》**

群里立刻热闹起来。

“又是月初公开处刑环节。”

“我上个月 31%，我已经准备好写检讨了。”

“低于 40% 的要参加培训，兄弟你完了。”

陆沉点开表格。

表格是按组排的，第一列是姓名，第二列是采纳率，第三列是“AI 生成代码行数占比”，第四列是“评审通过率”，第五列是“事故数”。

他往下拉，找到自己的名字。

**陆沉｜62.3%｜58.1%｜96.2%｜0**

组里排第三。

蒋文斌在群里发了两个字：“不错。”

后面跟着一串鼓掌的表情。

陆沉看着那个 62.3，看了很久。

他想起早上那一行判空。那是灵犀写的。他想起中午那段取数逻辑。那是他写的，但字段名是灵犀帮他从那张没有注释的表里猜出来的。他想起下午那个 MR 描述。那是他写的，写了三行，灵犀帮他扩成了七行，还加了一个“影响范围”小节。

他关掉表格，打开自己的提交记录，一页一页往前翻。

二月的提交，一月的提交，去年十二月的提交。

他想找一段完完全全由自己敲出来的代码。不是灵犀补全的，不是灵犀生成的，不是他复制粘贴改了两个变量名的。

翻了整整三页。

他没找到。
